# BlockCraft 文档设计

> Last updated: 2026-10-08

目标是让文档既有视觉层次，又能正常书写、改宽、删改栏目。先形成有表现力的视觉方案，再选择合适的原生能力承载；组件清单不是审美上限。可编辑性是交付目标，不等于只能用普通段落和细线。

## 先确定三件事

- **任务**：制作新文档、局部美化、整理全文，还是先给 HTML 示意。沿用已有内容、已确认风格及用户编辑范围；美化本身不授权改写事实、删除栏目或重建整篇。
- **风格**：语气、色彩、字形、材质、装饰密度。商务、花笺、拼贴都可有流式版本；风格不决定定位方式。
- **版式**：正文是否增长、页面是否调宽、是否用于固定纸张、哪些元素需独立移动。长文需要内容延展，但不必整页都是单列；封面、短文和主题手记可以探索固定构图或混合布局。流式/分页以及装饰强度由任务决定，不自动把简约单列作为通用答案。

信息足够时直接推进，只对影响结果的未知条件提问。给出的布局应能解释每个容器的用途：排文字、形成列关系、提供共同表面，或维持对象间几何关系。

## 选择制作路径

- **新建有设计感的文档、整篇美化、模板或封面设计**：默认走“真实内容与艺术方向 → 视觉探索 HTML → 能力映射与落地版 HTML → 同一份设计参数生成原生数据 → 实际文档对照修正”。先读下方视觉流程指南，不在编辑器中一边堆对象一边猜整体效果。
- **改字、调整一个标题/颜色、修复局部间距**：直接修改原生文档，不强制制作 HTML。
- **已有用户认可的 HTML/设计**：复用并核对能力和当前内容，不另起设计覆盖用户选择。

HTML 是制作过程中的视觉样稿，最终交付仍是用户要求的可编辑文档。用户只要示意时停在示意；已授权完整制作时，自检后继续原生实现，不默认增加“确认 HTML 才能继续”的审批环节。若当前环境没有 HTML 制作或预览能力，明确这一限制，使用结构与样式设计表继续可完成部分，不能声称已预览。

## 先做好看，再解决怎么做

视觉探索先受用户内容、阅读需求和明确交付尺寸约束。允许有表现力的字体、构图、图片穿插、材质、形状和层叠；不把“高级”固定理解为少颜色、细线、暖纸或大封面。HTML 尚不好看时，不因已经满足原生字段就进入交付。

能力标注在视觉方向形成后补充，默认展示干净的设计稿。区分真正的编辑器限制、Agent 暂未开放的操作、版本差异和 UI 操作困难；不要把后面几项误写成设计禁令。探索稿可保留待验证效果，必须如实标注；落地稿才逐项验证、等效替换或讨论缺口，不绕过执行权限。

## 能力判断

编辑器内 Agent：从本次 runtime 的 capabilityDirectory 找能力，使用 `blockcraft.get_capability` 读详情。技能讲设计决策，不授予新能力；`createParameters`、`writableProps`、`insert`、父子约束和当前工具才决定能写什么。完整编辑器支持的功能可能尚未开放给 Agent。

外部 AI：有原生工具就使用其当前合同；制作离线快照/集成时读取目标安装版本的 Schema 和公开 API。参考里的属性不是跨版本保证。不要通过 DOM、私有实例或直接修改 node_modules 绕开宿主编辑接口。

两种执行环境都应保留原生可编辑文字，保护已有行内材料、链接和用户内容。时间、人员、天气的来源与冻结行为取决于宿主，不能把某业务的模板意向当作 BlockCraft 通用协议。

## 交付

整体视觉任务先完成 HTML 自检，再在原生文档中试做能覆盖主要结构的一段/一个区域，确认可编辑性、样式继承和实际占位后再推广。按本次布局选择改宽、长文、删区、缩放或分页验证；证据不足时明确区分“数据已生成”“已应用”“已保存回读”“已视觉检查”。HTML 是示意，不是原生能力已验证的证明。
